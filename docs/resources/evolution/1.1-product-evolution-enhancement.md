# GenDev 1.1 Product Evolution Enhancement

Status: Concept note; not an authorized plan
Date: 2026-07-27
Target release: 1.1 (post-1.0.3)
Classification: Product evolution enhancement
Predecessor context: 1.0.2 distribution context remediation (published),
1.0.3 agent context remediation (drafted, pending review)
Provenance: design discussion of 2026-07-27, recorded here before the
reasoning decays

## What This Document Is

A record of a design conversation, written down so the reasoning survives
the gap between now and whenever 1.1 gets scoped. It's not a remediation
plan, it carries no work packages, and nothing in it is authorized. The
findings-and-acceptance discipline of a real plan comes later, after the
dependencies named at the end have been satisfied.

What follows is the argument for treating product evolution (rebuilds,
maintenance, change over time) as a first-class concern of the
methodology, along with the risks that argument has to survive.

## The Regeneration Thesis

Frontier coding models improve, and the release cadence has compressed.
That suggests a use for GenDev beyond preventing drift inside a single
build.

The gates split cleanly. G1 through G4 (vision, requirements,
architecture, governance) articulate what's being built, why, and within
what constraints. They're expressed in human language, approved by named
humans, and independent of any particular tool or model. G5 through G7
turn that articulation into a working product using whatever generator is
current.

If that split holds, the upper gates are a durable asset and the lower
gates are regenerable. A product could be forward engineered: amend the
specification where the business has moved, take advantage of a better
model or a better harness, and re-run the build gates to produce a new
implementation of the same intent. The specification becomes the source
and the code becomes a build artifact, which is a different relationship
than the one most teams have with their codebase.

The economic argument follows. Documentation-first methodology currently
justifies itself by drift prevention on one build, which is a diffuse
benefit competing against "prompt carefully and review well." Amortizing
the specification across several regenerations changes it from a tax into
capital.

## Why The Verification Specification Is The Load-Bearing Asset

Rebuilds don't usually fail at generation. They fail because nobody can
tell whether the rebuild is correct. Most teams contemplating a rewrite
discover that their only specification is the code they're replacing,
which turns the project into archaeology.

GenDev produces the missing oracle at G3. The verification specification,
the requirement traceability matrix, and the UAT scenarios are written
before any code exists and approved by a human. They describe correctness
independently of the artifact being replaced. The PRD is table stakes;
the verification specification is the differentiator, and the thesis
raises its stakes considerably. If it's weak, rebuild equivalence is
unprovable and the whole idea collapses. That argues for investing in its
rigor (concrete acceptance criteria, golden outputs, property statements)
beyond what the gate currently demands.

## Risks The Thesis Has To Survive

The deepest one is that the specification underdetermines the artifact.
Every real system carries decisions that never reached a document: the
threshold someone tuned after an afternoon of fiddling, the retry
backoff, the exact error text a downstream script greps for, the ordering
that happened to be stable. The spec says deduplicate similar items; the
implementation is a specific answer to a question the spec only gestured
at. A regeneration produces a different specific answer, satisfies the
spec, and behaves differently. This is why historical rewrites went
badly.

The second risk is the counterfactual. A regeneration isn't competing
with stasis, it's competing with the same improved model doing
incremental work on the existing codebase. Better models refactor,
extend, and test existing code well. Regeneration wins only when
accumulated architectural commitments tax incremental work heavily, or
when a new harness enables something structurally impossible before. That
window is narrower than every model release, and it probably looks like
every few years, triggered by architectural obsolescence rather than by a
version number.

Third, specification compatibility isn't behavioral compatibility. Users
and integrators depend on observed behavior, not documented behavior. The
thesis is strongest where the external surface is narrow and contract
defined (command line tools, batch pipelines, services with real contract
tests) and weakest where the surface is wide (interfaces with many
consumers, libraries with a long tail of callers).

Fourth, state. Regenerating something stateless is a clean experiment.
Anything with persisted data, schemas, and live users has a migration
problem the specification layer doesn't address. If regeneration is a
design goal, it belongs in G3 as an architectural constraint from the
start: the persistence boundary must be specification defined and version
tolerant, because a future build has to consume this build's data.

Fifth, ossification. If the specification becomes the treasured asset,
there's pressure to protect it, and the end state is a beautifully
preserved description of a product nobody wants. The pitch has to be that
the specification is cheap to change and then regenerate, not that it's
stable.

One historical objection will be raised by anyone who lived through it:
this rhymes with model-driven architecture, CASE tools, and round-trip
engineering, all of which failed. The distinction is that those attempted
formal generation, and the formality gap was unbridgeable. This bet is
natural-language specification plus a verification oracle plus a capable
generator, and the generator is precisely the component that changed.
That answer needs to be ready, and it needs evidence behind it.

## Rebuild As Specification Audit

The underdetermination risk has an unusual response available, and it may
be the most useful idea in this note.

The first regeneration is a specification audit. Every place the new
build diverges marks a decision that was never written down. Each
divergence gets a disposition (promote to the specification, accept as
incidental, or treat as a defect being fixed), and the specification gets
more complete. Regeneration fidelity should then rise with each cycle,
which converts the largest weakness into a defined mechanism with a
measurable output.

## The Altitude Question

An early framing put G3 at the center. That's incomplete. G5 holds two
kinds of content that behave very differently under regeneration.

The first is generator accommodation: phases sized for one agent session,
sequenced for context management, fenced so the model doesn't wander.
That content exists because of what the current tools can hold. Carrying
it into a rebuild is harmful, because it constrains a better model to the
limitations of a smaller one.

The second is decision resolution. The construction directive is the last
document before code, so it's where underdetermined choices actually got
settled: thresholds, ordering, error taxonomy, module boundaries. That
content is model independent and has to survive.

The useful consequence: if a rebuild needs something carried forward out
of G5, that's not evidence G5 is durable. It's evidence the decision was
filed at the wrong altitude. A choice that matters across implementations
is architecture and belonged in G3 or an ADR. A choice that matters only
to this build is scaffolding and can die with the build. So a regeneration
doubles as an altitude audit, and every divergence traceable to a
construction directive is a promotion candidate.

The same test applies to the phase plan. Where the partition maps onto
real seams (module boundaries, dependency ordering, deployment units),
it's architecture wearing a schedule's clothes. Where it's about session
size, it's scaffolding.

Candidate principle: durable decisions belong at or above the G4 line;
everything below it should be specific to this generator, this session,
this build. This also gives G7's review a question it doesn't currently
ask, which is whether any construction directive contains a decision that
should have been an ADR. That check earns its keep even for projects that
never rebuild anything, because misfiled decisions are hard to find later
regardless of why you're looking.

G5 artifacts retain provenance value independent of reuse value. Even
when the directives are discarded, they answer what the previous build
was told, which is the first question anyone asks when a regeneration
diverges.

## Configuration Management: The Gap And The Asymmetry

GenDev today is a one-way walk from G0 to G9, and then the map ends.
There's no treatment of what happens to the gate artifacts across
maintenance releases, feature branches, and successive builds.

The irony is that GenDev already performs rigorous configuration
management on exactly one repository: its own. The lifecycle registry is
a baseline record. The release index is a supersession chain with
tag-conditional binding. The synchronization targets are cross-artifact
version agreement with mechanical enforcement. The installation record
binds a methodology version to specific file digests. None of that ships
to the projects GenDev governs. It's the same shape as the distribution
context finding from 1.0.2: the methodology solved a problem for itself
without recognizing that its customers have it too.

Four primitives are missing, and they're separable.

The baseline. Configuration management's core object is a named, frozen
set of item versions, and nothing today says that product release 1.4.0
was built from vision at this revision, PRD at that one, architecture at
another, these directives, this code. Gate log events bind approvals to
commits and provenance pins bind artifacts to sources, so the raw
material exists; nothing assembles it. The regeneration thesis needs
exactly this, because rebuilding "the product" is meaningless until you
can name which configuration constituted it.

Re-entry. After G9 a change arrives. A copy tweak shouldn't re-walk G1; a
new subsystem probably should. There's no loop-back rule today. Blast
radius classification is the obvious hook since it already expresses
proportionality, but nobody has drawn the mapping.

Artifact version identity. Artifacts are mutable files whose history
lives in git rather than in themselves. That's adequate until two
releases are alive at once, at which point people need to speak about the
PRD as of 1.3 versus as of 1.4 without trading commit hashes.

Branch arbitration. Two branches amending the PRD is a governance merge,
not a text merge. One existing mechanism helps more than it gets credit
for: provenance staleness fires at merge time, so if a branch moves the
PRD, every artifact pinned to it goes stale and the checker names them.
That's automatic detection of governance drift across branches. It tells
you something needs re-approval. It doesn't tell you who decides.

## Shift Left Applied To Configuration Management

Conventional configuration management assembles the record at release
time: someone stops, inventories the build, and writes it down. That's
archaeology with a deadline, and it's why the discipline is universally
resented.

GenDev's gates already write durable records as they close, each carrying
a reviewed revision, an approver, and a checked statement. Provenance
pins already bind artifacts to source versions. The phase ladder already
records what each increment was told to do. Nearly every fact a baseline
needs is already being written, at the moment it's true, by people with
the context to write it.

So the central question for 1.1 is probably not what new records teams
must maintain, but what projection is needed over records already
emitted. That gives a clean scoping test: if a record can be generated
from data the repository already holds, it's a candidate for inclusion;
if it requires a human to maintain a parallel ledger, it's out, or it's
wrong. This is the same discipline that produced the provenance tool in
1.0.2. When the system can compute a value it enforces, the practitioner
shouldn't be transcribing it.

## Change Management: Proportional Amendment

Changes vary (defects, minor features, major features, business-driven
scope shifts), and the artifact response should vary with them. A minor
feature shouldn't require rewriting the PRD; an addendum should serve.

The reason to prefer addenda over rewrites isn't economy of effort. A
rewrite destroys evidence. Replace the PRD and the record of what was
approved, by whom, against what risk disposition survives only in git
history, which nobody reads as governance. An addendum leaves the
original approval intact and adds a second approval with its own date,
approver, and checked statement. The result is a chain of decisions
rather than a series of overwritten files.

The known failure mode is amendment accretion. After a dozen addenda,
answering what the product requires today means reading the base plus
twelve amendments in order and performing the merge mentally. Provenance
improves while legibility decays, until someone rewrites everything in
frustration and discards the chain.

What rescues it is something GenDev already enforces for unrelated
reasons. Stable REQ-NNN identifiers, mandated at G2 and never permitted
to change, mean an amendment can be scoped to identifiers rather than
prose regions: REQ-007 is superseded by this text, REQ-023 through
REQ-027 are added, REQ-011 is withdrawn with rationale. Once amendments
are identifier scoped, the consolidated view stops being an editorial
exercise and becomes a computation. The identifier discipline was built
for traceability and turns out to be the change management primitive.

Architecture already has a working version of this. ADRs are additive and
dated, and one supersedes another by reference. The pattern doesn't need
inventing so much as generalizing to the artifacts that lack it.

On classification, a taxonomy is probably the wrong starting point. The
useful question isn't which of four labels a change wears, but which
gate's artifact it invalidates. A defect fix touching only code
invalidates nothing upstream. A feature that fits the existing
architecture invalidates the PRD but not G3. A feature that doesn't fit
invalidates the architecture, which makes it an ADR rather than an
addendum. A change that moves the success criteria invalidates the
vision. Candidate rule: re-enter at the highest gate whose artifact the
change invalidates, walk forward from there, and let blast radius set the
rigor of each re-entry. That derives the taxonomy instead of imposing
one.

Adoption caution: in a mature product most changes are defects, and if
every defect costs a governance artifact the methodology gets routed
around within a quarter. Defects should mostly cost a test and a
traceability update. The judgment worth teaching is distinguishing a
defect from a latent requirements defect, meaning the code did what the
PRD said and the PRD was wrong. The first costs nothing upstream. The
second is a requirements change wearing a bug report's clothes, and
pretending otherwise is how specifications go stale while everyone
follows the process.

## The Defect Log As Regeneration Input

This is not a proposal to build a defect tracker. Organizations have
those, and a worse one embedded in a methodology would fragment the
record and go stale.

The purpose is different. The specification says what the product should
do. The defect history says where reality disagreed with someone's
reasoning about it, and that knowledge cannot be derived by thinking
harder about the PRD. Feed a regeneration only the specification and it
starts from the same beliefs the first build started from, which means it
gets to rediscover the same surprises, on production traffic, one at a
time. The defect log is accumulated empirical correction, and discarding
it at rebuild time would be the most expensive mistake this thesis could
make.

Defects sort into three classes by regeneration value. Some reveal the
specification was wrong or silent, and those shouldn't remain defects at
all: they get promoted into the amendment path so a new build never
inherits the error. Some are implementation failures where the
specification was right and the builder was wrong; those are hazard
markers, telling a fresh agent where a competent implementer went off the
road. The third class is the valuable one: defects discovered only
through contact with the world (a feed emitting malformed dates, a
case-insensitive filesystem, an upstream service lying about its content
type). No amount of specification rigor produces those. They were
purchased with incidents, and they're the closest thing a software
product has to institutional memory.

On integration, the principle is that GenDev owns the binding, not the
record. The defect lives in the organization's tracker. The repository
needs a durable, checkable reference to it, plus the content the tracker
has no slot for: what the agent was instructed to do, what changed, what
evidence the quality gates produced, and who accepted the fix against
what statement. That shape is familiar (instruction, build, evidence,
human acceptance), which suggests a compressed phase rather than a new
artifact class.

Two constraints. Zero overlap: if the fix record repeats title, reporter,
severity, and status, it's dual bookkeeping and one copy will rot.
Offline validation: the checker can enforce that fix commits carry a
well-formed work item reference without touching the network, and any
actual tracker integration must remain a team-owned, optional step,
because requiring credentials would turn a governance tool into an
integration dependency. Also worth generalizing: features arrive from the
same trackers as defects, so the primitive is an external work item
reference, not a defect reference.

## Tests And The Regeneration Line

Which side of the line tests live on decides whether defect knowledge
survives.

If tests are build artifacts, regenerated with the code, every lesson
encoded in a regression test evaporates at rebuild. The new
implementation writes new tests reflecting new assumptions and the old
scars vanish. If the regression suite is promoted above the line and
attached to the verification specification, the defect history is carried
automatically and enforced mechanically. The rebuild doesn't receive
advice about the malformed date; it receives a failing test until it
handles the malformed date. That's the difference between context and
enforcement.

So two tiers. An executable tier holds defect-derived and
verification-derived tests, preserved across implementations and
mechanically enforced. A narrative tier holds lessons that can't be
expressed as tests (design approaches that seemed right and weren't,
sequencing hazards, why a boundary sits where it sits), distilled for
agent context rather than exported raw, because ticket prose written for
humans mid-triage is nearly useless to a builder.

Two constraints on the executable tier. Preserved tests have to be
behavioral, exercising the system at its boundary with concrete inputs
and expected outputs; unit tests coupled to internal structure will fail
a reorganizing rebuild for reasons unrelated to correctness. And not all
automated tests deserve preservation: tests an agent wrote alongside the
code encode that agent's reading of the specification, including its
misreadings, so preserving them would grade a rebuild against the
original builder's misunderstanding. Tests earn preservation by having an
origin outside the implementation, which means defect-derived tests are
the most trustworthy artifacts available, precisely because nobody
reasoned them into existence.

A useful side effect: teams chronically under-invest in writing a
regression test for a fix, because the fix already works and the test
feels like paperwork. Under this model a test is the only mechanism that
guarantees the defect can't return in a future build.

## User Acceptance Testing Is The Human Floor

Machine-automated user acceptance testing is not achievable by
methodology alone, and the reason is structural rather than about
tooling.

Automated tests answer whether the system does what the specification
said. User acceptance testing answers whether the specification was
right. Generate UAT from the specification and execute it mechanically
and you've built a loop that can only confirm the specification, which
means it passes cleanly on the day the product is precisely wrong. The
gap between what was specified and what the business needed is the entire
thing UAT exists to detect, and no artifact derived from the
specification can detect it.

There's a second reason that isn't about verification. Acceptance is an
accountability act: someone with standing says this is good enough to put
in front of users, and their name goes on it. That signature isn't a slow
implementation of a check a machine could do faster.

Consequences for the design. The two classes stay separate with different
mechanics on a rebuild: the automated behavioral suite is machine
enforced, while UAT scenarios are preserved above the regeneration line
but executed and signed by people. Tooling stays external (whether
execution lives in a dedicated test management product, a spreadsheet, or
a checklist is not GenDev's concern), while the evidence shape is
specified: which scenarios, against which build, run by whom, on what
date, with what outcome, traced to requirement identifiers. The G7 final
test and UAT artifact already occupies that slot.

The realistic lever isn't automation, it's scoping. With requirement
identifiers on scenarios, a rebuild touching three subsystems knows which
scenarios must be re-run and which are untouched. That makes the human
cost proportional instead of total. It doesn't reach zero, and it doesn't
fall when the models improve. Human acceptance is the floor on
regeneration economics, and anyone pitching rebuilds as cheap is quietly
assuming that cost away.

Trap worth naming, because it looks like progress: translating UAT
scenarios into an executable specification syntax, wiring them to a test
runner, and declaring UAT automated. What results is a
developer-maintained integration suite wearing business language,
reviewed by nobody in the business, drifting from what users care about
while producing green checkmarks. More test infrastructure, less
acceptance.

## Making It Measurable

The thesis currently rests on argument, which is the weakest footing
anything in this project has stood on.

Proposed measurement: regeneration fidelity, defined as the fraction of
UAT rows and requirement traces that pass on a rebuild without amending
the specification. The distribution matters more than the scalar, because
where the failures sit determines which machinery is worth building.
Divergences traceable to post-acceptance tweaks argue for the delta
capture apparatus. Divergences traceable to choices made inside the
original build and never touched since are invisible to commit history
and argue for golden-output differential testing instead. Low fidelity
overall argues that G3 is too thin to support regeneration, which is a
change to the methodology's front half rather than an addition to its
back half.

The experiment is cheap and available. The dogfood project is small,
stateless, and its G1 through G4 artifacts already exist. Build it
through G7, then rebuild from the same upper gates with a different agent
or model, measure fidelity, harvest divergences into the specification,
and rebuild again to see whether the second number beats the first. As
far as we're aware nobody has published that measurement.

## Note On Git As Delta Capture

Commit history helps, and GenDev makes it more useful than usual because
commits are gate anchored: commits inside a phase are directive bound and
traceable to requirements, while post-G7 commits that aren't themselves
gate governed are by definition the undocumented delta. That set can be
generated rather than excavated.

Two limits. Git records the change, not the constraint: a commit reading
"tune threshold to 0.85" gives the value and maybe a local reason, but
not whether 0.85 is required or merely adequate. Mining produces
candidates for amendment; a human still adjudicates. And the absence of a
commit is invisible: decisions baked into the original build and never
touched afterward arrived inside a phase-build commit looking exactly
like the deliberate ones. Those are precisely the underdetermined choices
most likely to diverge, and only differential testing surfaces them.

One precondition deserves stating because it's usually violated by
default. Squash merging collapses the granularity this depends on. Under
this thesis, commit-history fidelity stops being a stylistic preference
and becomes a requirement, alongside requiring that post-acceptance
changes to governed source carry a disposition.

## Candidate Scope Boundary

Likely in scope for 1.1: a generated baseline manifest; product release
identity with a tag; artifact version identity as of a release;
identifier-scoped amendment with a computed consolidated view; re-entry
rules keyed to blast radius; external work item binding; preserved-test
tier definition and UAT evidence shape.

Likely out of scope: change control boards, change request forms, impact
analysis matrices, a standalone configuration management plan artifact,
any required network integration, and anything resembling automated user
acceptance testing.

Undecided and needing a decision before scoping: branch arbitration
(detection is mechanical, adjudication is a human policy question about
who owns a contested amendment); whether the preserved test tier is
mandatory or opt-in; and whether regeneration is presented as a supported
methodology path or merely as a property the artifacts happen to enable.

## Dependencies And Sequencing

This waits behind 1.0.3, and it wants evidence before it wants design.
The runbook-versus-code coherence test produces the first full G0 through
G7 traversal. A regeneration measurement on that same project produces
the fidelity number. How much re-entry and delta-capture machinery is
worth building depends on what a second cycle actually costs, and
scoping this release before running the experiment would let the plan
drive the evidence instead of the other way around.
